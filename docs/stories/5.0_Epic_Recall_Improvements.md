# Epic 5.0: Improve Recall Through Multi-Pass Blocking and Address-Aware Prefiltering

## Epic Overview

**Goal:** Improve duplicate detection recall (find more true duplicates) without significant runtime impact by implementing controlled multi-pass blocking and address-aware Stage-2 prefiltering.

**Status:** Planning

**Priority:** High

**Estimated Effort:** 2-3 weeks

---

## Business Context

The current duplicate detection system uses a single-pass address-based blocking strategy. While this is fast and effective for many cases, it misses legitimate duplicates in two key scenarios:

1. **"Moved" cases:** Same person at different addresses (different PLZ/street)
2. **"Strong address, noisy name" cases:** Clear address match but borderline name similarity (60-70%)

These gaps reduce **recall** (the percentage of true duplicates we find), which is critical for fraud detection where missing a duplicate can mean missing fraudulent activity.

---

## Current System Limitations

### Problem 1: Single-Pass Blocking Misses "Moved" Cases

**Current Behavior:**
- Blocking uses address-based keys: `plz_street`, `plz_only_...`, `street_only_...`
- Records with different PLZ/street are never compared unless one has incomplete address
- For records with no address, phonetic blocking is used: `phon_{vorname_phon}_{name_phon}`

**What's Missed:**
```
Person A: Hans Müller, Bahnhofstrasse 10, 8001 Zürich
Person B: Hans Müller, Seestrasse 5, 6000 Luzern

→ Different blocking keys (different PLZ + street)
→ Never compared
→ Duplicate missed (despite identical names and birth date)
```

### Problem 2: Stage-2 Prefilter Rejects Good Candidates Too Early

**Current Behavior:**
```python
# Stage-2 fuzzy matching in process_block_worker
1. Check business rules (Zweitname, date)
2. Calculate name similarity
3. If name_score < fuzzy_threshold (70%): REJECT ← Problem here
4. Only then compute address_ratio and confidence
```

**What's Missed:**
```
Person A: "Meyer, Hans" at "Bahnhofstrasse 10, 8001 Zürich"
Person B: "Mayer, Hanss" at "Bahnhofstrasse 10, 8001 Zürich"  (typo in first name)

→ Name similarity: 65% (below 70% threshold)
→ Address ratio: 100% (perfect match)
→ Rejected at Step 3 before address is considered
→ Duplicate missed despite strong address evidence
```

---

## Proposed Solution

### Story 5.1: Multi-Pass Blocking (Pass A + targeted Pass B)

Add a controlled second blocking pass using phonetic name codes + birth year for records where Pass A is weak.

**Key Innovation:** Only generate Pass-B keys for hard-to-match records:
- Records with `plz_only_...` or `street_only_...` keys (incomplete address)
- Records with phonetic blocking (`phon_...`)
- AND effective birth year is present (keeps blocks bounded)

**Expected Impact:**
- Recall improvement: +8-15%
- Performance impact: +10-15% (controlled by selective Pass-B generation)

### Story 5.2: Address-Aware Stage-2 Prefilter

Make Stage-2 fuzzy prefilter compute address evidence for borderline name scores and only reject when both name AND address are weak.

**Key Policy:**
- If `address_ratio >= 0.75`, allow `name_score >= 0.60` to proceed
- Otherwise maintain current `fuzzy_threshold` (70%)
- Add new match types: `address_assisted_normal` and `address_assisted_swapped`

**Expected Impact:**
- Recall improvement: +3-8%
- Performance impact: +2-5% (minimal - just computes address slightly earlier)

### Story 5.3: Code Cleanup and Legacy File Organization

Move legacy files (`duplicate_checker_integration.py`, `duplicate_checker_poc.py`) to `legacy/` folder and update documentation to clarify the "active" codebase.

**Expected Impact:**
- Better code organization
- Clearer for new developers
- Reduced confusion about which files to use

## Success Criteria

### Quantitative Metrics

1. **Recall Improvement:** +10-20% more true duplicates found
2. **Performance Impact:** <20% increase in total processing time
3. **Precision Maintained:** False positive rate remains <5%
4. **Test Coverage:** All existing tests pass + new test cases for edge cases

### Qualitative Metrics

1. **Clear Match Types:** New match types clearly indicate why pairs matched
2. **Documented Behavior:** Clear documentation of multi-pass blocking logic
3. **Maintainable Code:** Clean separation of concerns, well-commented
4. **Production Ready:** Feature flags to enable/disable new features

## Risk Assessment

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| Performance degradation >20% | Medium | High | Feature flags to disable; benchmark extensively |
| False positive increase | Medium | High | Conservative thresholds; manual review of sample |
| Pair duplication in results | High | Medium | Pair deduplication step in analyze_duplicates() |
| Block size explosion | Low | High | Sub-blocking by year; max block size limits |
| Code complexity increase | Medium | Medium | Clear abstractions; comprehensive testing |
